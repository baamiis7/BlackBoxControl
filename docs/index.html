🏗Architecture Overview

BlackBoxControl is a Windows WPF desktop configuration tool for fire alarm control panels manufactured by BAAMIIS LTD. It connects to an ESP32 microcontroller over USB-serial and transfers panel configuration using a custom binary framed protocol. Projects are saved locally as .kbb files (JSON).

Platform: Windows 10+, .NET 9, WPF · Pattern: MVVM with manual DI

Data Flow — Save Project

User clicks Save
  → MenuViewModel.SaveCommand
  → ProjectMapper.ToProjectData(panelViewModels)     ← conversion
  → IProjectService.SaveAsync(path, projectData)
  → File.WriteAllTextAsync(path)  →  .kbb (JSON)

Data Flow — Upload to Device

User clicks Upload
  → UploadConfigurationViewModel.UploadCommand
  → ProjectMapper.ToProjectData(panelViewModels)
  → ConfigurationUploadService.UploadAsync(data, serialService)
      → SendPacketAsync(HANDSHAKE)     → WaitForAckAsync (5 s)
      → SendPacketAsync(PANEL_CONFIG)  → WaitForAckAsync (2 s)
      → SendPacketAsync(LOOP_CONFIG)   → ACK  × N loops
      → SendPacketAsync(DEVICE_CONFIG) → ACK  × N devices
      → SendPacketAsync(BUS_CONFIG)    → ACK  × N buses
      → SendPacketAsync(BUS_NODE_CONFIG) → ACK × N nodes
      → SendPacketAsync(CE_HEADER / CE_INPUT / CE_OUTPUT) → ACK
      → SendPacketAsync(END_TRANSMISSION)

📡Binary Serial Protocol

Source: Protocol/BinaryProtocol.cs  ·  Baud: 115 200  ·  MCU: ESP32

Packet Frame Format

Every packet uses the same framing regardless of type:

START0xAA1 byte
TYPE0x01–0xFF1 byte
LEN_Hhigh1 byte
LEN_Llow1 byte
PAYLOADtype-specific data0 – 512 bytes
CHECKSUMXOR1 byte
END0x551 byte
FieldSizeDescription
START1 byteAlways 0xAA
TYPE1 bytePacket type constant
LEN_H1 bytePayload length, high byte (big-endian)
LEN_L1 bytePayload length, low byte
PAYLOAD0–512 bytesType-specific data
CHECKSUM1 byteXOR of all payload bytes
END1 byteAlways 0x55

Minimum packet size: 6 bytes (zero-length payload). Max payload: 512 bytes.

Checksum Algorithm

byte checksum = 0;
foreach (byte b in payloadBytes)
    checksum ^= b;  // XOR of payload only — START/TYPE/LEN/END not included

Upload Sequence

PC ESP32 │ │ │──── HANDSHAKE (0xF0) ───────────────────────►│ timeout: 5 000 ms │◄─── ACK (0xF1) ───────────────────────│ │ │ │──── PANEL_CONFIG (0x01) ───────────────────►│ timeout: 2 000 ms each │◄─── ACK (0xF1) ─────────────────────────────│ │ │ │──── LOOP_CONFIG (0x02) × N loops ─────────►│ │◄─── ACK each ───────────────────────────────│ │ │ │──── DEVICE_CONFIG (0x03) × N devices ───────►│ │◄─── ACK each ───────────────────────────────│ │ │ │──── BUS_CONFIG (0x04) × N buses ─────────►│ │◄─── ACK each ───────────────────────────────│ │ │ │──── BUS_NODE_CONFIG (0x06) × N nodes ───────►│ │◄─── ACK each ───────────────────────────────│ │ │ │──── CE_HEADER (0x07) ───────────────────────►│ per C&E rule │──── CE_INPUT (0x08) × N ───────────────────►│ │──── CE_OUTPUT (0x09) × N ───────────────────►│ │◄─── ACK each ───────────────────────────────│ │ │ │──── END_TRANSMISSION (0xFF) ────────────────►│
If ESP32 replies NACK at any step, upload is aborted immediately. If no reply arrives within the timeout, upload is also aborted.

.kbb File Format

.kbb files are UTF-8 JSON serialised from ProjectData. The extension stands for BlackBox Konfiguration.

{
  "ProjectName": "Site A — Building 1",
  "Panels": [
    {
      "PanelName": "Main Panel",
      "Location":  "Ground Floor, Room 1",
      "Loops": [ /* Loop objects */ ],
      "Busses": [ /* Bus objects */ ],
      "CauseAndEffects": [ /* C&E rule objects */ ]
    }
  ]
}
All conversion between ViewModels and ProjectData is done exclusively in Services/ProjectMapper.cs. Never add conversion logic elsewhere.

⚙Services

IProjectService / ProjectService

Responsible for saving and loading .kbb project files. Pure file I/O — no conversion logic.

interface IProjectService
{
    void   Save(string filePath, ProjectData data);
    Task   SaveAsync(string filePath, ProjectData data);
    ProjectData? Load(string filePath);
    Task<ProjectData?> LoadAsync(string filePath);
}
  • Uses Newtonsoft.Json for serialisation
  • Async overloads use File.WriteAllTextAsync / File.ReadAllTextAsync
  • Called only from MenuViewModel

Single source of truth for converting between ViewModels and the ProjectData DTO.

MethodDirection

ToPanelViewModels(projectData)DTO → ViewModels (load / download)

SerialCommunicationService (real hardware)

Opens System.IO.Ports.SerialPort at 115 200 baud.

  • SendPacketAsync — serialises BinaryPacket.ToBytes() and writes to port
  • WaitForAckAsync — TaskCompletionSource-based (no polling): creates a TCS, SerialPort.DataReceived fires, buffers bytes, parses ACK packet, calls _ackTcs.TrySetResult(isAck)
  • Uses Task.WhenAny(tcs.Task, Task.Delay(timeout)) for timeout

MockSerialCommunicationService (simulator)

Used during development or when no hardware is connected. Two Channel<BinaryPacket> replace polling:

ChannelPurpose
_ackChannelReceives ACK/NACK packets; read by WaitForAckAsync
_dataChannelReceives config packets; read by ReceivePacketAsync

Activated by calling ISerialCommunicationService.EnableSimulator().

ConfigurationUploadService / DownloadService

Orchestrates the full upload/download sequences using ISerialCommunicationService. Works identically with real hardware or the mock — no if (isMock) branching.

Adding a New Theme

  1. Copy GreenTheme.xaml to e.g. Themes/RedTheme.xaml
  2. Update the ~20 color brush values
  3. Register the name "Red" in ThemeManager
  4. Add a menu item in MenuViewModel / MainWindow.xaml
Always use DynamicResource (not StaticResource) for color brush references in form XAML. Static references are not updated when the theme changes at runtime.

📝ADR-001: MVVM with Manual DI

✓ Accepted

Context

The application needs testable ViewModels, swappable services (real serial vs. simulator), and clear separation between UI and business logic.

Decision

Adopt MVVM throughout and use manual dependency injection in App.xaml.cs.OnStartup() rather than a DI container.

Rationale

The object graph is small and shallow — a DI container adds complexity without benefit. Manual wiring is explicit and easy to trace for a small team. The ISerialCommunicationService and IProjectService interfaces are sufficient to enable unit testing without any container.

Consequences

Positive: ViewModels are independently testable · Serial hardware swappable for simulator · No DI NuGet dependency
Negative: Adding a transitive dependency requires manually threading it through constructors · No lifetime management (all objects are app-lifetime singletons)

📝ADR-002: Custom Binary Framed Protocol

✓ Accepted

Context

The PC tool must transfer structured configuration data to an ESP32 with limited RAM (512-byte packet limit) and no OS-level framing.

Decision

Use a custom binary framed protocol with fixed start/end markers, 2-byte big-endian length, XOR checksum, explicit packet type byte, and per-packet ACK/NACK handshake.

Rationale

Binary vs JSON/XML: Significantly smaller payloads; ESP32 does not need a JSON parser. Per-packet ACK: Fine-grained error recovery. XOR checksum: Sufficient for single-bit error detection on short-range USB-serial. Start/end markers: Allow receiver to re-synchronise after noise.

Consequences

Positive: Small payloads fitting ESP32 RAM · Simple to implement on both sides · Deterministic upload time
Negative: Both sides must be updated in lockstep on packet format changes · XOR does not detect all multi-bit errors (acceptable for wired USB)

📝ADR-003: BaseStyles + Per-Theme Color Files

✓ Accepted

Context

The application originally had three theme files each containing 300+ lines of duplicated XAML control templates. Any style change required editing three files. The only difference between files was ~20 color values.

Decision

Extract all control templates into a single Themes/BaseStyles.xaml. Each theme file becomes ~20 lines of color brush definitions that merge BaseStyles. All color references in BaseStyles use DynamicResource. LogicGateIcons.xaml is merged inside BaseStyles (not App.xaml) to ensure it is always reloaded on theme switch.

Consequences

Positive: 3×300 → 1×300 + 3×20 lines · Adding a theme requires only a color palette · DynamicResource means theme switching works at runtime without restart
Negative: All themes share identical control shapes (acceptable — branding is color-only) · DynamicResource has a small runtime lookup cost vs StaticResource (negligible)
